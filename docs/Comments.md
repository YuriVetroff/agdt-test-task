## Структура решения

В солюшен-файле два основных блока проектов - Core и Medical. Своего рода доменное разбиение. В Core лежит базовый код, Medical (и любой другой потенциальный блок) использует его для конкретных реализаций. Некоторые проекты в Core содержат принципиальное описание какой-то функциональности (например, DataAccess), а некоторые служат маркерами для единообразия внешних зависимостей (как в случае с Mapping и MediatR - пакеты подключаются единым способом и имеют одну версию).

Если расширять такой подход на большое решение, то Core и Medical следует разносить в отдельные солюшены/репозитории и связывать через Nuget-пакеты, используя какое-нибудь хранилище артефактов.

Каждый конкретный блок (в нашем случае Medical) придерживается следующей структуры:
1. AgdtTestTask._{BlockName}_.Common - опциональный проект с базовым кодом (интерфейсы, перечисления, хелперы);
2. AgdtTestTask._{BlockName}_.Entities - проект с сущностями;
3. AgdtTestTask._{BlockName}_.DataAccess.Abstracts - опциональный проект с абстракциями доступа к данным на случай, если нужно расширить репозиторий;
4. AgdtTestTask._{BlockName}_.DataAccess.EF - EntityFramework-реализация доступа к данным (контекст, конфигурация сущностей, при необходимости - реализация кастомного расширения репозиториев);
5. AgdtTestTask._{BlockName}_.DataAccess.Migrations - исполняемый проект для миграций;
6. AgdtTestTask._{BlockName}_.BusinessLogic.Abstracts - абстракции бизнес-логики (интерфейсы, DTO);
7. AgdtTestTask._{BlockName}_.BusinessLogic - реализация бизнес-логики (конкретные классы, маппинг, конфигурации);
8. AgdtTestTask._{BlockName}_.MediatR - проект для реализации паттерна MediatR для установления слабых связей (в нашем случае используется для связи веб-части и бизнес-логики);
9. AgdtTestTask._{BlockName}_.WebApi - веб-приложение с API.

Любой дополнительный код (например, реализация поиска даты по Fhir) добавляется отдельным проектом со следующим наименованием: AgdtTestTask._{BlockName}_._{ProjectName}_.

Юнит-тесты пишутся под конкретный проект и именуются по схеме AgdtTestTask._{BlockName}_._{ProjectName}_.Tests.

*Покрывать юнит-тестами каждый метод в рамках тестового задания было бы слишком долго. Для примера я сделал тесты для метода поиска по дате. Проект с тестами - AgdtTestTask.Medical.Fhir.Tests. Используется библиотека xUnit.*

## Доступ к данным

Для доступа к данным используется Entity Framework в связке с SQLServer. Реализация с двойной вложенностью - контекст EF недоступен на уровне бизнес-логики, а вся работа с данными производится через репозитории (CRUD и querying) и фасад (транзакции). Для репозитория используется стандартный набор операций, при необходимости его можно расширить кастомными методами (поэтому класс `EFRepository<T>` оставлен публичным).

Используется подход Code First. Миграции реализованы в виде консольного приложения с вызовом метода `context.Database.MigrateAsync()`. В качестве альтернативы (более правильной) можно было бы использовать migration bundle, но консолька удобнее при первичной разработке и отладке.

## Модель данных

Если строго следовать json-структуре из условия, то получается примерно следующая модель данных: у Patient связь one-to-many с Name, у Name связь one-to-many с GivenName. Реализовывать такой вариант в чистом виде было бы не очень правильно, потому что для каждого бизнес-действия пришлось бы вызывать дополнительные джоины (что-то вроде `Include(x => x.Name).ThenInclude(x => x.GivenNames)`), плюс схема данных была бы намного сложнее из-за явного описания этих связей. Вместо этого очень удобно использовать подход OwnsOne/OwnsMany, когда одна сущность является составной частью другой:

    builder.OwnsOne(p => p.Name, n =>
    {
        n.ToTable("PatientName");
    
        n.WithOwner()
            .HasForeignKey("PatientId");
    
        n.OwnsMany(n => n.Given, g =>
        {
            g.ToTable("PatientGivenName");
    
            g.WithOwner()
                 .HasForeignKey("PatientId");
    
            g.HasKey("PatientId", "Value");
        });
    });
В данном случае сущности Name и GivenName являются зависимыми от Patient и генерируют таблички PatientName и PatientGivenName соответственно, а их основным идентификатором становится внешний ключ PatientId. Используя EF, при чтении данных пациента данные имени подтягиваются автоматически.

## API
Классическое веб-приложение ASP.NET Core WebAPI. Есть контроллер PatientController со всеми методами, есть вью-модели для разных сценариев. Для доступа к бизнес-логике из контроллера используется паттерн MediatR.

Вью-модели для пациента и имени повторяют контракт DTO из уровня бизнес-логики. Можно было бы сделать интерфейсы наподобие `IPatientContract`, `INameContract` и в целом использовать интерфейсы почаще, но во-первых, без контекста дальнейшего развития приложения это сложно, а во-вторых, мне было просто лень :) Поэтому DTO всего две - `PatientDTO` и `NameDTO`, и используются они для всех трёх сценариев (чтение, добавление, редактирование). Вью-моделей побольше, потому что для создания и частичного редактирования требуется разная валидация.

Трансформация вью-моделей в DTO и обратно производится с помощью Automapper (как и на уровне DTO <-> Entity). Например, для имени используется вот такой код:

    CreateMap<NameCreatingVM, NameDTO>();
    CreateMap<NameUpdatingVM, NameDTO>()
        .ForMember(
            dst => dst.Given,
            opt =>
            {
                opt.PreCondition(
                    src => src.Given != null);
                opt.MapFrom(
                    src => src.Given);
            });
Так сделано для того, чтобы автомаппер автоматически не создавал пустую коллекцию для Given, если с клиента пришло значение null, и в дальнейшем не обнулял имена в базе при частичном редактировании. Аналогичный подход использован и на уровне бизнес-логики. В целом, автомаппер очень классный инструмент и для реализации различных CRUD-операций сильно упрощает жизнь (а ещё можно использовать проекции ProjectTo для сложных запросов к данным...).

Согласно заданию требовалось реализовать следующие методы:
1. создание пациента;
2. редактирование пациента;
3. удаление пациента;
4. поиск пациента по идентификатору;
5. поиск пациентов по дате. 

С этим есть небольшой нюанс, т.к. методы редактирования и удаления требуют некоего ключа для установления идентичности пациента, а поле Id в имени является опциональным. К счастью, у сущности пациента есть собственный обязательный первичный ключ, и в методах Update и Delete я использую его (для этого пришлось расширить вью-модели и DTO пациента свойством Id). Не знаю, имелось в виду по условию именно это или нет, но концепция не сильно меняется в любом случае.

## Поиск по дате (Fhir)
Ключевая функциональность. Согласно условию, нужно было реализовать поиск по дате как здесь: https://www.hl7.org/fhir/search.html#date.

Любое решение так или иначе сводится к динамическому построению предиката, если мы хотим искать это на уровне базы. Основная реализация лежит в классе `FhirSearchExtensions` (проект AgdtTestTask.Medical.Fhir). Сигнатура входного метода следующая:

    IQueryable<T> BuildDateSearchExpression<T>(
        this IQueryable<T> query,
        IEnumerable<string> birthdateParams,
        Expression<Func<T, DateTime>> dateSelector)
Здесь `query` - исходный запрос к данным, `birthdateParams` - набор поисковых параметров согласно контракту Fhir, а `dateSelector` - служебная функция, которая указывает, по какой именно дате мы ищем (чтобы не делать какой-то интерфейс вроде IHasBirthdate и не прибивать к нему гвоздями механику поиска).

Для первичной обработки используется подход с парсингом входных строк с помощью регулярного выражения, по итогу чего из набора вида [ eq1985, gt1985-02-01 ] строятся пары [ Equal  (1985-01-01; 1986-01-01), GreaterThan (1985-02-01; 1985-02-02) ], где первое значение (Equal/GreaterThan) - это тип условия для поиска, а второе - интервал времени. Необходимость использовать интервалы вызвана тем, что технически Fhir ищет не по конкретной дате, а именно по интервалу, и длительность интервала определяется уровнем глубины даты (если указан только год, то искомый интервал будет равен году, если месяц - то месяцу, и так далее). Сделать это красиво с помощью LINQ или каких-то встроенных механик DateTime не получилось, поэтому пришлось заниматься ручным парсингом строки с датой, основной код находится в методе `ToInterval`.

Далее для каждой пары вызывается метод построения поискового запроса `BuildSearchExpression`, где в зависимости от типа условия строится `Expression` с использованием встроенных методов `AndAlso`, `LessThanOrEqual` и так далее. Для префикса "ap" (приблизительный поиск) используется более сложный метод `BuildApproximateMatchExpression`. В итоге у нас получается финальный `Expression`, который мы возвращаем в следующем виде:

    return Expression.Lambda<Func<T, bool>>(match, parameter);

Применяется этот код в бизнес-логике:

    var patients = await patientRepository.ApplyQueryAsync(
        x => x.BuildDateSearchExpression(birthdateParams, p => p.Birthdate));
        
Нижележащий метод репозитория транслирует этот код на уровень базы:

    public async Task<IEnumerable<T>> ApplyQueryAsync(
        Func<IQueryable<T>, IQueryable<T>> queryBuilder)
    {
        return await queryBuilder(_set.AsQueryable()).ToListAsync();
    }
